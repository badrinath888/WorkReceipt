# Interaction audit (v0.4.1)

Machine-readable matrix: `docs/interaction_matrix.json` (screen, control, expected, handler, dependency, test, level, status, reason),
regenerated by `python3 -m pytest test_interaction_audit.py`. Levels: **browser** = real click/keys in headless Chrome against the real
HTTP server on synthetic data; **backend** = direct engine/HTTP call; **packaged-macos** = needs the real .app. A FakeNative host
stands in for the window, so native-dependent controls are PASS only for "page → HTTP → host call → UI result"; the Cocoa side is BLOCKED.

Totals: 69 rows — PASS 60, FAIL 0, BLOCKED 9.

## Root cause of the Mac "Native folder dialog unavailable"
Every native action depended on pywebview's JS bridge (`window.pywebview.api`), which exists only if pywebview's post-navigation script
injection succeeds inside the frozen app. On the Mac that never became ready (no error is surfaced anywhere), so Choose… stayed disabled.
Not reproducible on Linux. Fix: native actions no longer use the JS bridge. They go over the app's own token-protected loopback HTTP
channel (`/api/native/status|pick_folder|open|reveal`) to a Python `Native` host that holds the window privately. The page enables pickers
when `/api/native/status` says the window was *shown*. Menu items use `run_js` (not `evaluate_js`, which waits for the bridge).
Drag-drop uses a Python DOM drop handler → `window.wrDropped(path)`; it is optional and BLOCKED until tested on Mac.
